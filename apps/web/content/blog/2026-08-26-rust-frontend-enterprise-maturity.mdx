Most framework comparisons measure the wrong thing. They benchmark render throughput, count GitHub stars, and then a procurement reviewer asks "what is your accessibility conformance report, what is the support window, and who fixes a CVE in the render layer on a Friday" — and the benchmark answers none of it. This report scores the Rust frontend stack the way the *Rust & AI Weekly* radar scores crates: **stewardship first, features last**, with an Adopt / Trial / Assess / Hold verdict and a metadata block naming who pays for the code, what shipped last, and when.

The theme is one sentence: **framework risk is stewardship risk, not benchmark risk.** Every axis below either has a primary artifact behind it or it is marked as unestablished. Vendor blogs and SEO listicles were used to find leads and then discarded — the Rust frontend space in 2026 is full of content-marketing pages carrying wrong version numbers, and half the "2026 comparison" articles cite Leptos 0.6.

*(Version and download figures pulled from the crates.io API on August 26, 2026. Everything else links to a primary source.)*

## How this report is scored

Nine axes. Each one names the artifact that answers it, because an axis you cannot evidence is an axis you are guessing at.

| # | Axis | Primary evidence — not opinion |
|---|------|-------------------------------|
| 1 | Stewardship and bus factor | `git shortlog -sne --since=12.months` on the upstream, the funding page, org sponsors, OpenSSF best-practices badge |
| 2 | Release cadence and semver honesty | crates.io / npm version history with dates, the breaking-change list per minor, whether a migration guide exists |
| 3 | Support window | the *published* policy. Angular and Electron have one. Dioxus, Leptos, Tauri and egui do not — which means you are the LTS |
| 4 | Security posture | external audit PDFs in-repo, advisory count and fix latency, `cargo audit` / `cargo deny` against *your* lockfile |
| 5 | Supply chain | transitive dependency count, unmaintained-crate advisories in the tree, whether an SBOM can be generated from the lockfile |
| 6 | Accessibility | a screen-reader matrix you ran yourself, plus a VPAT 2.5 / ACR you could actually publish. Not a Cargo feature flag named `accessibility` |
| 7 | Enterprise operations | code signing and notarization, MSI/MSIX, auto-update with rollback, crash symbolication, telemetry policy and its opt-out |
| 8 | Measured cost | wasm or binary size, cold start, resident memory, build wall-clock — measured in *your* repo, never quoted from a hello-world |
| 9 | Hiring and handover | can a TypeScript team maintain it, are the docs LLM-ingestible, is there a third-party component supply |

**Three kill-shot axes.** Any red here is a Hold regardless of the other six: accessibility on a customer-facing surface, code-signing plus update on a distributed binary, and an unpatchable advisory sitting in your dependency tree. A framework that scores well on everything else and cannot pass a procurement accessibility review is not a candidate; it is a prototype.

**The evidence pass, so anyone can re-run it:**

```bash
cargo audit                            # RustSec against YOUR lockfile, not the upstream's
cargo deny check                       # advisories + licenses + duplicate versions
cargo tree -i glib -e no-dev           # who drags the GTK3 chain into your build
cargo cyclonedx --format json          # the SBOM your procurement questionnaire asks for
git shortlog -sne --since=12.months    # bus factor, run inside each upstream clone
gh api repos/tauri-apps/tauri/security-advisories --jq '.[].summary'
twiggy top pkg/app_bg.wasm             # where the bytes actually went
```

"Vanilla" is ambiguous in the way that matters, so this report scores two of them. **Vanilla-A** is the incumbent every Rust proposal is actually competing against: TypeScript and React in a browser, wrapped in Electron when it needs to be a desktop app. **Vanilla-B** is the Rust control group: `wasm-bindgen` and `web-sys` with no framework at all, which is the honest way to ask "how much of the risk is Rust and how much is the framework."

## The Rust candidates

### Tauri 2.11.5 — Adopt, as the shell

Tauri is the only candidate in this report with a published external audit, and it has two. [Radically Open Security audited v1 in 2022](https://github.com/tauri-apps/tauri/blob/dev/audits/Radically_Open_Security-v1-report.pdf) and delivered a v2 penetration-test report dated Amsterdam, August 7 2024, [published in-repo as a PDF](https://github.com/tauri-apps/tauri/blob/dev/audits/Radically_Open_Security-v2-report.pdf) and funded by NLnet via NGI. The findings were not cosmetic — the mobile development server exposed the developer's disk to the local network without authentication, Android dev mode skipped certificate validation, and the isolation pattern's IPC signing key was extractable from JavaScript — and all of them were closed before v2 stable. That is the shape of a healthy security process: findings published, severity owned, fixes shipped ahead of the stable tag. On top of it, the project [documents its own release discipline](https://v2.tauri.app/security/ecosystem/): internal review of security-relevant PRs before minor and major releases, signed commits, mandatory maintainer approval.

The capability model is the enterprise draw. Every filesystem path and native feature a frontend can reach is declared in configuration, so an auditor reads a manifest rather than grepping a codebase. The cost of that model, and it is a real one, is that a missing capability surfaces as a silently rejected promise rather than a loud error — budget onboarding time for it.

The axis-5 finding you must own: on Linux, Tauri's webview inherits the gtk-rs GTK3 binding chain, and that chain carries `RUSTSEC-2024-0412` / `-0413` / `-0416` (unmaintained GTK3 bindings) plus [`RUSTSEC-2024-0429`](https://rustsec.org/advisories/), an unsoundness in `glib::VariantStrIter` **with no patched version available**. This is not a Tauri defect — it is upstream GTK3 bindings being end-of-life — but it lands in your `cargo audit` output and therefore in your risk register. Document it with a `cargo deny` exception that names the reason and expires.

*Maintenance: active, multi-maintainer, Commons Conservancy programme; audits externally funded (NLnet/NGI) · Latest: 2.11.5 (Jul 1, 2026), v2 stable since Oct 2, 2024 · Adoption: **Adopt** as the shell around a web surface. It is the only candidate whose security claims survive contact with a published pen-test report.*

### Dioxus 0.7.10 — Trial, and be honest about the tax

Dioxus is the most interesting Rust UI project and it is not an Adopt. What it has going for it is genuine: a funded team (Satellite.im, FutureWei, Y Combinator, GitHub Accelerator, ~$500k tracked), a [0.7 release](https://dioxuslabs.com/blog/release-070/) with 350+ merged PRs shipping hot-patching, a WGPU native renderer, automatic Tailwind and a first-party `llms.txt`, and an [0.8 roadmap](https://github.com/DioxusLabs/dioxus/discussions/5024) that reads like a team who knows which parts are weak — native platform APIs, cross-platform parity, bug fixing.

What keeps it at Trial is the axis-2 and axis-3 story. [The 0.7 migration guide](https://dioxuslabs.com/learn/0.7/migration/to_07/) lists breaking changes to form submissions, asset options, custom server-function errors, the prelude, the default server-function codec, owned event listener types, and the outright removal of the `dioxus-lib` crate. That is a normal pre-1.0 minor for this project, which is the point: at roughly two minors a year, a migration is an annual line item, and the 1.0 on the roadmap is explicitly scoped to *a subset of the API for library authors* rather than the framework you would be shipping. There is no support window, no security-advisory process to point a reviewer at, and no named enterprise reference customer.

One item that will come up in a policy review and that almost nobody flags: **the 0.7 CLI ships opt-out telemetry.** It reports invoked commands with arguments stripped, per-stage build timings, heartbeats and crash reports with local paths stripped. The mechanism is legitimate and the rationale is reasonable — the CLI grew into a bundler and hot-patcher and rare panics were invisible in GitHub issues — but "opt-out" means your CI images and developer laptops phone home until someone turns it off. Turn it off explicitly, in the image, and write down that you did: `dx config set disable-telemetry true`, or `DX_TELEMETRY_ENABLED=false`, or build the CLI with the `disable-telemetry` feature.

*Maintenance: small full-time team, corporate + VC funded, single dominant maintainer · Latest: 0.7.10 (Jul 31, 2026); 0.8 cycle open · Adoption: **Trial** for a web or fullstack surface you own end-to-end. Not Adopt: pre-1.0 breaking minors, no support window, no external audit, no published reference customer.*

### Dioxus Native / Blitz — Assess

The WGPU-backed HTML/CSS renderer is the most ambitious thing in Rust UI and the least ready. `dioxus-native` is at 0.7.x with ~6.6k downloads a month, the [Blitz repo](https://github.com/DioxusLabs/blitz) carries the bleeding edge, and accessibility is wired through AccessKit in `blitz-shell` and on by default. On-by-default is not conformance: there is no published screen-reader matrix — no NVDA, JAWS, VoiceOver or Orca results — and the API docs still carry a "features that are not guaranteed to be supported" surface. For anything customer-facing, this is the axis-6 kill shot until someone publishes test results.

*Maintenance: same team as Dioxus, rapid churn, git ahead of crates.io · Latest: 0.7.x · Adoption: **Assess**. Prototype-grade for a product surface; interesting for internal tools where you control the audience.*

### Leptos 0.8.20 — Assess, downgraded from Trial

This is the report's clearest verdict change, and it comes from the maintainer rather than from a benchmark. The [May 2026 status update](https://github.com/leptos-rs/leptos/issues/4707) says plainly that Leptos is not abandoned but will be **lightly maintained** going forward, that it already does what its author set out to do, that maintaining a popular open-source project is draining, and that a `leptos_0.9` branch of cleanup and semver-breaking fixes is moving slowly.

That candour is exactly what this radar rewards — it is the same virtue that earned OxiSH an honest Assess in *Weekly #9* rather than a punishment. But candour does not change the operational consequence: on the best fine-grained-reactivity SSR framework in Rust, **you now own bug-fix duty**. That is an Assess, and any team already in production on 0.8 should be budgeting for a maintained internal fork rather than waiting for 0.9.

*Maintenance: light, by the maintainer's own statement (May 2026) · Latest: 0.8.20 (Jul 18, 2026) · Adoption: **Assess**, downgraded. Technically the strongest web-only option in Rust and the weakest stewardship story among the actively-used ones.*

### Yew 0.23.0 — Hold

Oldest, largest community, most third-party material, slowest cadence — 0.23.0 in March 2026 and 358k downloads over 90 days against Leptos's 1.24M. Virtual-DOM diffing where the rest of the field moved to signals. Yew is where you land if your constraint is "the most tutorials exist for it," and that is not an enterprise-maturity argument.

*Maintenance: community, slow · Latest: 0.23.0 (Mar 10, 2026) · Adoption: **Hold** for new work.*

### egui 0.36.1 and Iced 0.14.0 — internal tools only

egui is genuinely healthy on stewardship: 0.36.1 in August 2026, 5.0M downloads over 90 days, well-known commercial usage in Rerun. Iced is slower (0.14.0, December 2025) with a distinct Elm-ish architecture and a smaller ecosystem. Both fail axis 6 for anything customer-facing — immediate-mode and custom-widget GUIs render pixels, not an accessibility tree, and neither can host a DOM-based SDK. That last constraint is decisive for the verified-meeting case below.

*egui — Maintenance: active, well-used commercially · Latest: 0.36.1 (Aug 7, 2026) · Adoption: **Trial** for internal tooling and debug surfaces, **Hold** for anything a customer or a regulator sees.*
*Iced — Latest: 0.14.0 (Dec 7, 2025) · Adoption: **Assess**.*

### Vanilla-B: `wasm-bindgen` + `web-sys` — Trial

125M downloads in 90 days. This is not a framework, it is infrastructure, and it is the correct control group: it isolates "Rust in the browser" from "a pre-1.0 Rust UI framework." You hand-roll everything above the DOM, which is only sane for a bounded surface — a media pipeline, a crypto worker, a canvas widget. The strategic version of this verdict is the one several teams land on: keep the UI in TypeScript, put the Rust where Rust wins, and skip the framework question entirely.

*Maintenance: infrastructure-grade, Rust-org adjacent · Latest: 0.2.127 (Aug 8, 2026) · Adoption: **Trial** for bounded surfaces; the fallback that de-risks every other row in the table.*

## The JavaScript comparison, honestly

You cannot score Rust maturity without scoring what it must displace, and the JavaScript field changed in 2026 in a way that raises the bar.

**React 19.2.x — Adopt.** The governance story moved: the [React Foundation launched February 24, 2026](https://react.dev/blog/2026/02/24/the-react-foundation) under the Linux Foundation, with React, React Native and JSX out of Meta's ownership, platinum members including Amazon, Microsoft, Vercel, Expo, Callstack, Huawei and Meta, and a five-year Meta commitment of over $3M plus engineering. Technical governance sits with maintainers via a provisional leadership council, separate from the board. For a risk register, the relevant fact is not the foundation — it is React's support behaviour: [security fixes are backported to every affected major, with no security-only phase and no hard cutoff](https://react.dev/versions). Latest line is 19.2.8 (July 21, 2026). There is no React 20.

**Angular 22 — Adopt, if what you want is the policy.** Angular publishes the most formal lifecycle in the field: 18 months per major, 6 months active plus 12 months LTS taking only critical and security fixes, weekly patches, one-to-three minors per major. As of 2026, 22.1.2 shipped August 13, Angular 21 is in active support, 20 is in LTS. Downstream libraries peg their own windows to it. If your procurement questionnaire has a row for "vendor support lifecycle," Angular is the framework that fills it in without a conversation.

**Vue 3 — Adopt, with the EOL precedent worth reading.** Vue 2 went EOL at the end of 2023 and the core team endorsed a commercial continuation, pointing users at HeroDevs Never-Ending Support built and maintained by Vue core team members. That is the pattern to note, not the version.

**Svelte 5, Solid, Qwik — Assess, on thin evidence.** These did not surface primary governance or lifecycle artifacts in this pass. Absence of evidence is not a negative verdict; it is an unfinished axis, recorded as such.

**Electron — Adopt, with a treadmill.** [Majors every 8 weeks](https://www.electronjs.org/blog/8-week-cadence) tracking Chromium, and [support for the latest 3 stable lines only](https://www.electronjs.org/docs/latest/tutorial/electron-timelines), where the newest gets all fixes and older lines get backports as bandwidth allows. That is roughly a 24-week support life per major, so an enterprise baseline should mandate an upgrade every two majors (~16 weeks) to keep one version of slack. Most Electron CVE exposure is inherited Chromium/V8, so remediation is version-mapping rather than patching. Pinning to the oldest supported line is the worst posture available: least backport coverage, zero buffer to EOL.

**The comparison that matters.** Angular and Electron publish a support window; React publishes indefinite security backports; Vue proved a commercial EOL path with core-team endorsement. **Not one Rust UI framework in this report publishes any of the three.** That single row is the enterprise-maturity gap, and it is not a code-quality claim about Rust.

The adjacent non-web options — Flutter, Kotlin Multiplatform, .NET MAUI, Capacitor — are deliberately out of scope here, for one reason: the security section below turns on hosting a DOM-based SDK, and each of those changes that constraint rather than satisfying it.

## Closing the gaps — with standard practice, not invention

Every gap above has an established answer. None of them requires inventing process.

**1. Accessibility → publish an ACR, gate with axe, prove with assistive tech.** The procurement artifact is an Accessibility Conformance Report produced from ITI's VPAT template — the VPAT is the blank form, the ACR is the completed document, and vendors without one are routinely disqualified at RFI stage. VPAT 2.5 (November 2023) aligns to WCAG 2.2 and ships WCAG, Section 508, EU (EN 301 549) and INT editions; publish INT. It retired "Supports with Exceptions" for "Partially Supports" and added an explanation column, which formalizes a written justification per row. In CI, `axe-core` is the regression floor — it covers WCAG 2.0/2.1/2.2 A through AAA and analyzes the rendered DOM including Shadow DOM. Do not let its pass rate drive your conformance claims: Deque's own study of 13,000+ pages puts automated detection at **57.38% of issue volume**, which is not the same as success-criterion coverage, and other analyses put real WCAG-failure coverage at 30–40%. Guided/semi-automated testing pushes toward ~80%; the rest is manual and assistive-technology work. Note also that `axe-core` targets HTML — a Rust *native* renderer needs a platform-accessibility-tree ruleset instead, which is why Blitz and egui are Hold for customer-facing surfaces. Regulatory clock, for planning: DOJ's ADA Title II rules require WCAG 2.1 AA, with deadlines extended in April 2026 to April 26 2027 (entities serving 50,000+) and April 26 2028 (smaller).

**2. Support window → accept that you are the LTS, and fund it.** No Rust UI framework offers one. The JavaScript world solved this commercially — HeroDevs Never-Ending Support ships drop-in replacements preserving the exact public API for EOL Angular v4–v19, AngularJS, Vue 2 and 20+ other stacks, with severity-mapped SLAs and HIPAA/PCI/SOC2/FedRAMP framing — and no equivalent exists for Dioxus, Leptos or egui. The standard substitutes, in order of cost: pin exact versions and commit the lockfile with no automatic updates; budget a maintained internal fork for the framework you depend on most (this is now the correct default for Leptos 0.8); buy an upstream support contract where the maintainers offer one (Dioxus explicitly invites enterprise contact and lists enterprise support in its funding mix); and write a standing "upgrade every N months" line into the team's capacity, because a pre-1.0 dependency without one silently becomes a rewrite.

**3. Missing external audit → the funded-audit route is real and it worked.** Tauri did not pay for its own pen-test; NLnet/NGI did, and the Sovereign Tech Agency and Trifecta Tech Foundation are funding the same class of work elsewhere in the Rust ecosystem. If you depend on a Rust UI framework at a level where an audit is load-bearing, the leverage is co-funding one with the maintainers and requiring the report be published in-repo, exactly as Tauri's is. Cheaper signals to demand meanwhile: an OpenSSF best-practices badge, an OpenSSF Scorecard run against the upstream repo, and a security-advisory process you can point a reviewer at.

**4. Supply chain → a four-step ladder, roughly one engineering day.** Run `cargo audit` in report-only mode for two weeks to learn your exposure without blocking merges; switch to `cargo deny` blocking high and critical advisories, with license policy in `deny.toml`; generate an SBOM in the *release* workflow (CycloneDX via `cargo-cyclonedx` as the default, since it is what commercial scanners and procurement questionnaires accept — add SPDX only when a contract demands it, and note that `cargo-cyclonedx` invokes Cargo internally, so do not point it at untrusted projects); add `cargo-vet` only if your criticality warrants audit-sharing. Generate the SBOM on release, never on demand — a stale SBOM is worse than none. The compliance drivers are no longer hypothetical: the EU Cyber Resilience Act requires manufacturers to maintain SBOMs for connected products, CISA mandates machine-readable SPDX or CycloneDX for federal software, and DORA and NIS2 questionnaires now ask directly.

**5. Measured cost → measure it, and stop quoting hello-worlds.** The published "65 kB Dioxus hello world" does not survive a router; practitioners report 275 kB for a release hello-world with LTO and `opt-level = "z"`, and ~600 kB for a small multi-page SPA with no I/O. Build your own artifact, then: `wasm-opt -Oz` (10–30% typical, and skipping it leaves you 2–3× larger than necessary), `strip = true` (DWARF can double a binary), panic strategy, brotli on the wire, `twiggy top` to find where the bytes went, Lighthouse for the number a user experiences. For cross-framework rendering claims, use `js-framework-benchmark`-style harnesses and compare Rust frameworks against each other — WASM-versus-JS memory numbers are measured differently enough to be misleading.

**6. Migration tax → keep a breaking-change ledger.** For each candidate, list the breaking changes of the last three minors and the engineer-days each cost you. That table is your real annual dependency cost, it is the only honest input to a build-versus-buy conversation, and it takes an hour to produce from release notes.

## Security-practice compatibility: verified meetings, guest and host

This is where a generic maturity table stops being useful. A verified-meeting product — two parties in a call where liveness and identity are actually proven, not asserted — imposes constraints that eliminate most of the field before performance is discussed. The controls it needs, in the order they get harder:

1. **Liveness at the door.** A biometric SDK capture gate before the room opens, with the API secret server-side and the verdict fail-closed.
2. **Session integrity.** A room-scoped, single-use, short-TTL token in an `HttpOnly; SameSite=Strict; Secure` cookie, unreachable from JavaScript.
3. **Media-path integrity.** DTLS fingerprint pinning out-of-band, so a compromised signaling node cannot silently MitM "encrypted P2P" media. That requires reading the SDP-negotiated fingerprint from the running peer connection.
4. **Entry stream-binding.** The face that passed the scan is the face on the streamed track. Strongly, this means the SDK scans *the same* `MediaStreamTrack` that is added to the peer connection.
5. **Continuous liveness.** The face stays a live human, and a peer that stops proving it gets dropped — which needs something in the media path with authority.
6. **Content confidentiality past the middlebox.** Once anything sits in the media path, frame-level encryption becomes the difference between "the SFU routes ciphertext" and "the SFU sees the picture."

Now the compatibility matrix. Columns are the four surfaces a product like this can be built on; rows are the controls.

| Control | Browser + TS/React | Browser + Rust/wasm | Tauri webview | Rust native renderer (egui / Blitz) |
|---|---|---|---|---|
| Host a DOM-based biometric SDK (a custom element such as `<iproov-me>`) | ✅ native | ✅ via `web-sys` | ✅ (webview *is* a DOM) | ❌ **no DOM, no SDK** |
| Strict CSP without `unsafe-eval` | ✅ | ⚠️ needs `'wasm-unsafe-eval'` | ⚠️ same, plus the custom-protocol origin | n/a |
| `HttpOnly; SameSite=Strict` session cookie | ✅ | ✅ | ⚠️ origin is a custom protocol (`https://tauri.localhost` on Android), so `SameSite`/CORS assumptions need re-testing | n/a (no cookie jar) |
| `getUserMedia` camera + mic | ✅ | ✅ | ⚠️ **platform-fragmented** | ❌ (native capture crate instead) |
| DTLS fingerprint read from SDP for pinning | ✅ | ✅ | ✅ | ✅ (native stack exposes it directly) |
| `getDisplayMedia` screen share | ✅ | ✅ | ⚠️ no official plugin, forced picker | ❌ |
| Frame-level E2EE (`RTCRtpScriptTransform` + SFrame) | ✅ | ✅ **and this is where wasm wins** | ✅ where the webview supports it | ❌ |
| OS-level device attestation (App Attest / Play Integrity) | ❌ | ❌ | ✅ **only here** | ✅ |
| Bundle secret-leak scanning | grep `dist/` | grep `dist/` **and `strings` the `.wasm`** | both | binary scan |

Six findings from that table are worth stating outright, because each one has changed a design decision in practice.

**The DOM requirement eliminates the native renderers, full stop.** A browser-delivered biometric SDK is a custom element. `egui` renders pixels through WGPU and Blitz renders its own HTML/CSS tree without a JavaScript engine — neither can host a third-party web component, and no amount of maturity elsewhere fixes that. If your liveness vendor ships a web SDK, your frontend has a DOM. That is the single hardest constraint in this report, and it is why the Rust-native-GUI branch of the radar is irrelevant to this product class rather than merely immature.

**Rust in the browser costs you one CSP line, and it is defensible.** WebAssembly is blocked under a CSP unless `script-src` includes `'wasm-unsafe-eval'` (Chrome 97+, Firefox 102+, Safari 16+). The argument that wins the security review is precision: `'wasm-unsafe-eval'` permits `WebAssembly.compile` / `instantiate` / `compileStreaming` and *not* `eval` or `new Function` — you get WebAssembly without opening the JavaScript eval hole. Two policy-authoring gotchas: `'unsafe-eval'` anywhere in the policy **overrides** `'wasm-unsafe-eval'`, so a lax legacy directive silently widens you; and some toolchains' JS glue still calls `new Function`, which would force full `'unsafe-eval'` — `wasm-bindgen` output is well-behaved here, Emscripten-derived bundles frequently are not. If you ship the call surface as an embedded widget inside someone else's page, their CSP decides whether your wasm runs at all.

**Tauri buys attestation and pays for it in media-capture fragility.** This is the trade that decides guest-versus-host architecture. On the plus side, a native host app is the *only* surface that can reach App Attest or Play Integrity — which is the one credible answer to "client-side liveness sampling is only as trusted as the client." On the minus side, camera and screen capture are genuinely platform-fragmented: WKWebView's `getUserMedia` has a long history of being disabled when embedded ([wry #85](https://github.com/tauri-apps/wry/issues/85), [WebKit bug 208667](https://bugs.webkit.org/show_bug.cgi?id=208667)); Safari-family webviews withhold host ICE candidates until camera permission is granted, so you need TURN and an early `getUserMedia` call; WebKitGTK WebRTC rides on GStreamer's `webrtcbin` and community success reports involve hand-compiled WebKit builds; Android's WebView has a two-layer permission model where the OS prompt succeeding does not mean the WebView got access, needs `MODIFY_AUDIO_SETTINGS` or the microphone comes back `NotReadableError`, and requires the `tauri.localhost` origin in your CSP or media access is silently blocked. Screen share is worse: there is no official Tauri capture plugin, [`getDisplayMedia` forces the system picker with no source-id API](https://github.com/tauri-apps/tauri/issues/11272), and Windows apps using `contentProtected` have shipped a black-screen bug. **Conclusion: never assume the Tauri webview is a browser for media purposes. Gate every media capability behind a runtime `navigator.mediaDevices` capability check with a per-platform fallback, and verify each target webview yourself.**

**Frame-level E2EE is the one row where Rust/wasm is strictly the better tool.** The old `createEncodedStreams()` API is dead and removed from the spec; the standards-track replacement is `RTCRtpScriptTransform`, which shipped in Safari in 2022, Firefox around 117, and Chrome as part of Interop 2025. Native `SFrameTransform` **never shipped in any browser** even though [SFrame itself is now RFC 9605](https://www.rfc-editor.org/rfc/rfc9605.html) — so you implement SFrame yourself inside a script-transform worker. That is a per-frame cryptographic hot path in a Worker, which is precisely the shape of workload where compiling Rust to wasm beats hand-written JavaScript, and it argues for Vanilla-B (`wasm-bindgen` in the worker) regardless of what renders your UI. Watch `generateKeyFrame` interop between Safari and Firefox, and for multi-party, key management lands on MLS (RFC 9420). One honesty note for the marketing copy: if you hold the keys, this is not zero-knowledge E2EE — it protects users against middleboxes, not against you.

**The guest and the host need different answers, and that asymmetry is the design.** A guest joins from a link on an unknown device and must not be asked to install anything: that forces a browser surface, which forces a DOM, and it caps the achievable assurance at what a browser can prove — no OS attestation, self-reported client state, liveness that decays rather than enforces. A host can reasonably be asked to install: that unlocks device attestation, a native media pipeline that reads DTLS fingerprints directly, and screen capture that does not depend on a webview's mood. The correct architecture is therefore **not one stack** — it is a browser surface for the guest and an optional native host app, with the *same* server-side enforcement behind both, and every assurance claim scoped to the surface that earned it. A control the guest path cannot enforce is not a product feature; it is a badge.

**Secret-leak scanning must cover the wasm binary.** A CI gate that greps `dist/` for API keys is a solved problem in a JavaScript build; a Rust/wasm build puts string literals inside a `.wasm` module that `wasm-opt` will happily shrink and never sanitize. Run `strings` over the module in the same gate, and treat any binary that is *not* scanned as unscanned.

## What this report could not establish

- **No independent security audit exists for Dioxus, Leptos, Yew, egui or Iced.** Tauri is the sole audited candidate. Anyone claiming otherwise should be asked for the PDF.
- **No screen-reader conformance results for any Rust native renderer.** AccessKit being enabled by default is a wiring fact, not a conformance result. Nobody has published NVDA / JAWS / VoiceOver / Orca outcomes.
- **No named enterprise reference customers for Dioxus, and no 1.0 date for the full framework.**
- **No sourced governance or lifecycle artifacts for Svelte, Solid or Qwik** in this pass — an unfinished axis, not a negative verdict.
- **No head-to-head bundle-size table.** Every public number is either a hello-world or an anecdote. Yours has to be measured.

## The thought at the end

The Rust frontend field in 2026 has excellent code and almost no lifecycle. Dioxus ships a hot-patching cross-platform renderer that would have been science fiction three years ago, and it cannot tell a procurement reviewer how long 0.7 will receive security fixes, because nobody has decided. Leptos is the most elegant reactive model available in the language and its maintainer has said, in public and with more honesty than most vendors manage, that it is now lightly maintained. Tauri is the outlier, and the reason is instructive: it went and got audited, published the findings including the embarrassing ones, and wrote its release-review process down.

That is the whole gap in one comparison. Angular can tell you the date its current major stops receiving security fixes. React can tell you that every affected major gets a backport, forever. Those are not better engineering; they are *published commitments*, and they are the cheapest thing on this list to produce and the most expensive thing to fake — which is exactly why an enterprise buyer reads them first. The Rust UI ecosystem's next unlock is not a faster renderer. It is one framework publishing a support window and then honouring it for two years.

Until then, the defensible posture is the boring one: adopt the shell that has been audited, trial the framework whose migration tax you have measured and written into your capacity plan, keep the surface a customer touches on a DOM that has an accessibility tree, put Rust where Rust wins — the per-frame crypto in the worker, not the button in the toolbar — and never claim an assurance the guest's browser cannot actually prove.
