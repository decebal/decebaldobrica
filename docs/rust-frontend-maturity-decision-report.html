The performance premise inverts too. Wasm can't touch the DOM directly, so per-node work pays a boundary crossing every time. Frameworks batch. Hand-written web-sys doesn't until you build it. What this report won't give you is a ranking: all four Rust frameworks have implementations in the official js-framework-benchmark suite, their current Chrome 150 figures went unverified here, and the widely quoted "beats React" line is unverified with them. The mechanism is the argument. The genuine wasm win, CPU-bound work at roughly 2–3× on the right workload, is available from a worker either way.

RTCRtpScriptTransform is settled: Safari 15.4, Firefox 117, Chrome 141, Baseline since October 2025. Native SFrameTransform is not — Chromium's shipping thread said in August 2025 that no browser had shipped it, and the interface has since left the specification index. So frame encryption is code you write inside a script-transform worker, against RFC 9605. A per-frame crypto hot path is exactly where Rust compiled to wasm beats hand-written JavaScript, whatever renders the buttons. Crate supply is thin: an sframe crate exists with no maintenance signals, and mls-rs claims full RFC 9420 conformance while stating it has had no third-party audit.

One correction against an earlier draft of this report: WKWebView stopped being the getUserMedia blocker in iOS 14.3, when WebKit began exposing it to embedding apps that can natively capture and satisfy Apple's authorisation requirements. The frequently cited wry #85 and WebKit bug 208667 are years stale. Screen capture is the live constraint.

Code protection as a constraint

A product shipping protected client code has a second constraint layer, and it lands on the frontend choice rather than on the security team.

Six constraints that a browser-API comparison doesn't surface.
ConstraintWhat it does to the decision
Obfuscators cover JS and TS, never your wasm Commercial and open tooling alike operate on JS language constructs. Moving UI logic into Rust removes it from the category: you keep compilation as obscurity, and you lose self-defending checksums, anti-monkey-patch detection, domain locks and tamper telemetry.
One eval-based transform deletes the wasm CSP argument 'unsafe-eval' overrides 'wasm-unsafe-eval', so an eval-string transform anywhere on the page re-opens the hole. Avoidable by configuration: pick a no-eval target and AST transforms, then prove it with a report-only header.
Anti-tampering makes the bundler a hazard Self-defence checksums and SRI are both byte-exact. Re-minifying, transpiling or re-bundling a protected SDK fails at runtime in production rather than in the build. Load it from its own immutable URL with crossorigin, outside the bundle graph.
Anything appended after protection breaks both checks Obfuscate, then append an integrity payload, and the self-check no longer matches its own release while any pre-append hash is wrong by construction. Hash the final served bytes last, and document the ordering.
Protection runs in CI, so the unprotected path is the tested one Credentials live in CI, so local development exercises an unprotected bundle. One integration run against the protected artifact, or the anti-tamper misconfiguration ships.
Compliance counts scripts, not modules PCI DSS 6.4.3, mandatory since 31 March 2025, wants script authorisation, script integrity and an inventory with written justification. A wasm module is inventoried through its JS loader, which makes that loader the compliance artifact. Obfuscating your own code satisfies none of it.

Two checks from the codebase behind this report, for calibration. cargo audit is clean at 371 crates and zero vulnerabilities. The secret-scan gate greps the built bundle for backend key material, has already been hardened once against an exit code that made it report clean while real secrets sat in the bundle, and still runs with -I — which skips binaries, so the .wasm was never in scope. A JavaScript-era gate does not survive the move to a compiled frontend on its own, and nothing announces when it stops covering the thing it was written for.

Closing the gaps

  • Accessibility. Publish an ACR from the VPAT 2.5 INT template. Wire axe-core into CI as the regression floor, not as the evidence: Deque's own study of 13,000-plus pages reports 57.4% of issue volume but automated coverage of only 16 of the 50 WCAG 2.1 AA success criteria, which is the number your ACR has rows for. Guided testing reaches roughly 80%. The rest is manual and assistive-technology work.
  • Component libraries don't hand you an ACR. A conformance report describes a product with a defined interface, so Adobe publishes ACRs for products while React Spectrum documents accessibility per component and IBM Carbon records per-component status. What you buy is the pattern implementation and the AT testing behind it. You still write the report.
  • Support window. Nobody in Rust publishes one, so pick who owns yours: pinned versions plus a funded internal fork, an upstream support contract, or a maintained JavaScript framework. Choose none of the three and you've chosen the first by accident.
  • Audits. Tauri didn't pay for its own pen-test — NLnet did, via NGI. Co-funding one and requiring in-repo publication is the available lever. Cheaper signals meanwhile: an OpenSSF badge, a Scorecard run, a security-advisory process you can point at.
  • Supply chain. cargo audit in report-only mode for two weeks, then cargo deny blocking high and critical, then a CycloneDX SBOM generated in the release workflow, then cargo vet only if criticality warrants it. A stale SBOM is worse than none.
  • Measured cost. Build your own artifact and measure it. Dioxus documents the arc for its TodoMVC example: 2.36 MB in release, 310 kB with the stable size configuration, 234 kB on nightly, after wasm-opt -Oz. That's a todo list, so scale the expectation before anyone quotes a hello world at you.
  • Migration tax. List the breaking changes of the last three minors per candidate, with engineer-days attached. An hour from release notes, and it's the only defensible input to build-versus-buy.

What this report can't establish

Two independent research passes went after these, primary sources only. What stayed a gap is listed rather than filled by inference.

  • No independent security audit exists for Dioxus, Leptos, Yew, egui, Iced, AccessKit or wasm-bindgen. No in-progress NLnet, NGI, Sovereign Tech Agency or Prossimo engagement surfaced either. Wasmi got one in 2025, sponsored by the Stellar Development Foundation, so the funding route exists.
  • No screen-reader conformance results for any Rust renderer. egui's AccessKit support on Windows and macOS plus a 2022 Narrator demo is the strongest evidence in the set, and it still isn't a conformance matrix.
  • No OpenSSF Scorecard result or best-practices badge located for any Rust UI repository. Not found rather than absent.
  • No verified benchmark numbers. Dioxus, Leptos, Yew and Sycamore all have implementations in the official js-framework-benchmark suite; their figures in the current Chrome 150 run went unverified here, so the popular "beats React" line stays unverified too.
  • No reproducible web-sys DOM microbenchmark. The 2018 thunk numbers are too old to quote, and per-call overhead against a batched transfer isn't published.
  • No production bundle-size report. The Dioxus figures above describe a TodoMVC example from maintainer docs: 2.36 MB release, 310 kB with the stable size configuration, 234 kB on nightly.
  • No component library publishes conformance evidence. radix-leptos claims WAI-ARIA compliance in a README, and conformance reports stay product-scoped across every vendor checked.
  • No first-person retrospective, in either direction, on migrating off a bespoke frontend framework with cost figures attached.
  • No frontend-specific hiring data. Rust-wide figures (606 open roles in February 2026, about a 15% salary premium, 4–14 weeks to hire) come from analyst blogs, not surveys.
  • No purchasable support contract. Dioxus lists enterprise support as an intention with no published offering or price, and Tauri's statutes describe a project on a nil budget.

How this was researched

Registry figures come from the crates.io API. Everything else traces to a primary source: audit PDFs, maintainer statements, GitHub issues, standards documents, vendor lifecycle pages. Three external research passes fed this report and every claim that changes a verdict was re-checked against its source before landing, which caught two errors worth naming. One pass reported CVE-2026-25541 as a wasm-bindgen vulnerability; it is an integer overflow in bytes. Another reported that Rust frameworks are absent from js-framework-benchmark; the suite carries Dioxus, Leptos, Yew and Sycamore implementations among 185 keyed entries. Two claims in earlier drafts of this report were wrong in the same way and are corrected above: WKWebView's getUserMedia status, and a benchmark ranking taken from a forum comment.

The supply-chain number is local rather than quoted: cargo audit against the Dioxus-web codebase behind this report reports 371 crates and zero vulnerabilities. The GTK3 advisories discussed above arrive with a Tauri desktop target on Linux, not with Rust on the web.

Charts are plain HTML and CSS, so every value sits in the text layer and reflows with the page. Colours come from an ordinal ramp validated in both modes; status colours always ship with an icon and a label, never colour alone. Companion prose: the blog post of the same date.
